Title: Compat 156 (Python 3.14) Overview
Planned Rollout Start: December 2, 2026
Release Version: M56
Availability depends on the server rollout, which is expected to complete by Q2 2027.
1: Survey Versioning
The new survey compatibility level is 156. Surveys using compat="156" and p3="1" or later run on Python 3.14 instead of Python 2.7. This is a breaking change for survey code and custom resources. The updated Python version supports future product development and access to newer Python language features and libraries.
Python 3 code can be syntactically valid and still behave differently from the equivalent Python 2.7 code. Syntax conversion alone is not a complete migration. Review data types, operator results, collections, imports, and resource loading as part of the same upgrade.
1.1: Python Version and Existing Surveys
A survey's compatibility level determines its Python version. Existing surveys keep their current compatibility level and are not converted automatically.

1.2: Python Syntax and Behavior
Moving to Python 3 requires more than changing syntax. Review behavior that can affect survey logic, data, and calculations:
Use print(...) as a function and update except and raise syntax. The old <> inequality operator is replaced by !=.
Python 3 distinguishes text strings (str) from byte strings (bytes). Convert explicitly with the appropriate encoding at boundaries where data changes between text and bytes.
Dictionary methods such as .items(), .keys(), and .values() return views rather than Python 2 lists. Use membership tests instead of .has_key().
Replace xrange with range. Python 3 range remains reusable and indexable, while map, filter, and zip return iterators. Convert those iterators to a list when the code needs list behavior.
The / operator performs true division, while // performs floor division. For example, 5 / 2 is 2.5 and 5 // 2 is 2. Review quotas, calculations, rounding, and comparisons between unrelated types, such as numbers and strings.
Some modules have different names. For example, use urllib.request instead of urllib2. Use explicit relative imports when importing from within a package.
Do not replace every / with // mechanically. Floor division rounds down, so changing the operator can affect negative as well as positive operands. Confirm the required result for each calculation before applying a change.
Syntax conversion does not guarantee that an imported module is exposed in secure survey execution. Review the supported environment and test the code.

1.3: Custom Dynamic Questions, Logic Nodes, and Hooks
Standard-library dynamic questions and logic nodes are available at compatibility level 156, except for retired features. Review custom resources separately before upgrading.
Custom resources are not converted automatically. Keep the original Python 2 files and add Python 3.14 counterparts with updated code alongside them:

hooks.py

Dynamic question with a Python module

In a dynamic question's meta.xml, the <supports> tokens control availability by Python version. Use p2 to show the question at compat="155" and earlier, p3 to show it at compat="156" and later, or p2,p3 to show it in both ranges. If neither Python token is listed, the question can appear in both ranges but may fail or load without its Python code. These tokens declare intended support; they do not confirm that the code works. Existing question-feature tokens continue to apply.
Custom logic nodes and hooks without Python 3 counterparts are unavailable at compatibility level 156 and later. Not all dynamic questions have a code.py module. Dynamic questions share styles.xml, so @if and ${...} expressions must work in both Python versions when a resource supports both ranges.
Apply future changes and fixes to both copies when both versions are supported, and test each intended compatibility range.

1.4: Legacy Features
Compat level 156 requires Delphi data and omits some legacy functionality. Examples include non-Delphi data, optional question labels, and surveys where the SECURE file has been removed. Legacy integrations and tools are also unavailable.
Check for dependencies on legacy features before upgrading. Earlier compatibility levels remain subject to existing support and retirement rules.

1.5: Before You Upgrade
Inventory survey code in exec, conditions, virtuals, validation, onLoad, expressions, and styles. Identify custom resources and their dependencies.
Update Python 3 files, metadata, and code while retaining Python 2 files needed by earlier compatibility levels.
Run available compatibility checks and review their suggestions. The checks are not exhaustive.
Test a separate sandbox or copy at the target compatibility level end to end. Check branching, quotas, calculations, dynamic questions, hooks, and data exports as applicable. Test both versions when a resource supports both.
Perform manual quality assurance even when checks report no changes or issues. Move to production only after reviewing the code and resources and completing testing.
